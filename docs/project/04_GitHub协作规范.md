# GitHub 协作规范

## 仓库设置

- 仓库建议设为私有，提交验收前确认老师是否需要访问权限；
- 默认分支为 `main`；
- 三名成员均以自己的 GitHub 账号加入为协作者；
- 开启 Issues，使用仓库内模板记录功能和缺陷；
- 建议保护 `main`，至少要求一个审查后合并；若时间紧，可不启用强制检查，但仍保留 PR。

## 首批 Issues

1. 建立 Electron、React、TypeScript 工程并生成可启动窗口；
2. 定义 preload 白名单与共享数据契约；
3. 实现知识库选择、最近知识库与刷新；
4. 实现 Markdown 文件树和笔记读取；
5. 实现新建、重命名、保存和自动保存；
6. 实现安全 Markdown 预览；
7. 实现标题/正文搜索；
8. 实现 Wiki 链接与基础反向链接；
9. 实现应用回收站与恢复；
10. 建立单元、集成和核心端到端测试；
11. 生成 Windows 可运行程序；
12. 完成操作手册、项目报告、演示脚本和用户反馈。

## 有效签入计划

课程要求至少 10 次有实际修改量的代码签入。建议自然形成 12～18 次提交：工程骨架、IPC 契约、知识库、文件树、读取、新建/重命名、保存、预览、搜索、Wiki 链接、回收站、测试、打包和文档各自形成独立结果。三名成员都必须使用自己的账号提交，不能由一人代交全部代码。

## 可见结果

每个关闭的 Issue 至少关联以下一种证据：代码和测试、构建输出、截图、操作记录、测试报告、用户反馈或文档章节。Issue 说明中写清验收步骤，不能只写“完成”。
